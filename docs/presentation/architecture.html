FANTADAMUS
Behind the team sheet

How a question becomes a verdict

Fantadamus is a set of tools inside each player's Claude app. Claude collects the facts from approved sites; Fantadamus checks them, keeps them in a small lakehouse and does all the arithmetic. This page describes the version for two players now being built, and marks what already runs.

The shape

Claude collects, the tools decide

Each player's Claude app talks to the Fantadamus MCP server. Read tools answer from stored data; when something is missing they say what to read and where. Submit tools take the facts Claude found, and only facts that pass every check reach storage.

Why Claude collects

All season, Claude chat found odds, lineups and ratings with no API keys. In the MVP each player's own Claude does that reading, so Fantadamus needs no keys or scrapers of its own (ADR-0005).

Why the tools decide

Probabilities need to be precise and repeatable. Claude never computes one: it submits what pages say, then relays the engine's answer. All the arithmetic is tested Python.

Why collect once

Facts are stored with their source and time and shared. When one player refreshes Genoa's lineup news, the other's next question uses it too.

One question

From “Beto o Laurienté?” to a verdict

  1. Claude

    The player asks. Claude calls the read tool compare_players.

  2. Fantadamus

    The tool answers from gold, or returns a refresh plan: which facts are missing or stale, which approved pages have them, and which submit tool takes each one.

  3. Claude

    Says “refreshing Genoa's lineup news…” and reads those pages with its own web search and fetch.

  4. Claude

    Submits structured facts with the page's link, when the page was published and when it was read. It leaves a field empty rather than guess.

  5. Fantadamus

    Checks the contract, the source host, the player names and the quality rules. A rejection comes back with its reason; Claude fixes only what the reason names.

  6. Fantadamus

    Appends the submission to bronze, rebuilds silver and gold, and recomputes the engine's numbers.

  7. Claude

    Calls the read tool again and relays the verdict, the margin and the reasons, in the player's language.

Storage

Three layers, one direction

A medallion lakehouse, sized for two players: Parquet files read through DuckDB. Every table has a versioned contract, and facts only ever flow from bronze to silver to gold.

LayerHoldsRule
BronzeEach submission exactly as received, inside its envelope.Append-only. The same payload sent twice adds a second file; no file is ever rewritten.
SilverValidated rows, one per player, the latest by when the source was read.Invalid rows stay out and are reported with field-level reasons. Ties break on content, so the order facts arrive in never changes the result.
GoldThe data products the read tools serve, each row carrying its source links.Rebuilt from silver. Tests compare gold with reviewed golden files.

As-of queries

Questions about the past use captured_at, when the source was read, so a replay of last Saturday sees only what was known then.

Contracts with versions

Each contract is a strict pydantic model with a committed JSON Schema. A schema change without a version bump and changelog entry fails the build; a breaking change needs a major bump.

Why DuckDB and Parquet

Tests run in seconds with no AWS account. The same files and layout move to S3 when the server goes online.

The engine

Every player has three outcomes

planned · Phase 2

The method is the owner's own (docs/method.md). It works out the expected score for every outcome, sorts each role by one key, then simulates the formations your league allows.

OutcomeProbabilityWorth
Startsp_startExpected rating plus the priced bonuses.
Comes on, gets a ratingp_cameoA cameo's value, and it blocks his substitute.
No rating1 − p_start − p_cameoNothing: the first bench player in his role replaces him.
 
# the ordering key: sort each role by it; the eleven is the top, the bench the rest
key     = (p_start × E_start + p_cameo × E_cameo) / (p_start + p_cameo)

# the rating and the bonuses, priced apart
E_start = expected vote + bonus_goal × E[goals] + bonus_assist × E[assists] − malus_yellow × P(yellow)
E[goals] = team xG × goal share × minutes share      # team xG fitted from the match odds

The odds set the bonuses

Team xG comes from the 1X2, over/under 2.5 and both-teams-to-score lines, through a Poisson model with a Dixon–Coles low-score correction.

Shrink everything

Ratings, goal shares and team form are pulled toward a prior in proportion to the sample. Five games are as noisy for a team as for a player.

Tested on real calls

Its acceptance tests are six decisions from this season, including a brute-force proof that the key gives the best ordering.

Guardrails

Rules the code enforces

  • Approved sites only. A submission whose source host isn't one of the 13 on the reading list is rejected and nothing is written. Look-alikes such as fantacalcio.it.evil.example or https://fantacalcio.it@evil.example fail too; generated URLs test this on every run.
  • No getting round a block. The agent prompt forbids signing in, paywall workarounds and video transcripts. A page that can't be read is reported, never forced.
  • Facts, not pages. Bronze stores the submitted facts with their link. No page text is kept.
  • Pundits stay anonymous. The creators behind the pundit consensus are named only in private configuration outside the repository; a check scans every commit and push for their names.
  • A public repository with nothing private in it. No third-party data, league members' names or rosters, or secrets. gitleaks runs on every commit and push.

Hosting

On one Mac first, then AWS

MVP · first

The owner's Mac

The MCP server runs locally over stdio for the owner's Claude app. The lake lives in a git-ignored folder. No cloud needed.

MVP · Phase 3

Online for the second player

The same server as an AWS Lambda endpoint that both Claude apps connect to, with the lake on a private S3 prefix. How players sign in is decided in Phase 3.

v1 · later

Scheduled pipelines

Collection moves into the server on a fixture-driven schedule: Iceberg on S3, Glue, Athena, Step Functions and EventBridge, from licensed or permitted sources.

One shared account, fenced off

It uses the AWS account that runs gamegusto, isolated by the fantadamus- name prefix, a permissions boundary and a deploy role that can touch nothing else.

A budget alarm comes first

The first module applied creates a €20 monthly budget alarm. The planned resources cost under $0.10 a month; the alarm is there to catch mistakes.

The owner deploys

Nothing reaches AWS until the owner has seen the plan and approved it; CI never deploys on its own. Terraform and the region (eu-north-1) are proposals awaiting their decision records.
